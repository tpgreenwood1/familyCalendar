# Database

`prisma/schema.prisma`, Postgres (Neon). Every table below descends from one of two roots:
Better Auth's own tables, or `FamilyGroup`. There is no cross-family foreign key anywhere in
the schema — every domain table carries (or denormalizes) a `familyGroupId`, which is what
makes family-data-isolation a query-shape rule (see "Family isolation" below) rather than a
row-level-security feature.

## Two connection strings

`schema.prisma` declares `url = DATABASE_URL` (pooled, PgBouncer — used by the running app)
and `directUrl = DIRECT_URL` (direct — used by `prisma migrate`/`prisma db seed`, because
PgBouncer blocks the session-level commands the migration engine needs). Both currently point
at the same Neon database; in production they'd be Neon's pooled (`-pooler` in hostname) vs.
direct connection strings. Never route a migration through the pooler.

## Auth tables (Better Auth-owned)

`User`, `Session`, `Account`, `Verification`, `RateLimit` are generated by Better Auth
(`npx auth generate --config lib/auth.ts`) against the Postgres adapter — don't hand-edit a
field to "fix" it, regenerate instead so the shape stays in sync with whatever Better Auth
version is installed. `User` additionally carries this app's own relations
(`familyMembership`, `familyMember`, `createdInvitations`, `usedInvitations`,
`createdCalendarEvents`) added by hand alongside the generated fields. See `docs/AUTH.md` for
the full auth picture, including why `FamilyMembership`/`Invitation`/`InviteAttempt` are
purpose-built tables instead of Better Auth's organization plugin.

- **`FamilyMembership`** — links a `User` to a `FamilyGroup`. Unique on `userId` (not a
  composite key): one adult belongs to exactly one family (multi-family membership is out of
  scope, DesignSpec.md §5.1/§30).
- **`Invitation`** — hashed (`codeHash`, SHA-256), expiring (7 days), single-use invite codes.
  The plaintext code is returned exactly once, at creation. Consumption is an atomic
  conditional `updateMany` (`WHERE usedAt IS NULL`) in `lib/invitations.ts`, not a
  read-then-write, to close the race between two people redeeming the same code at once.
- **`InviteAttempt`** — a bare `(key, createdAt)` row per join attempt, used only to compute a
  5-attempts-per-15-minutes rate limit (`lib/invitations.ts#assertInviteAttemptAllowed`).

## `FamilyGroup` and the household roster

**`FamilyGroup`** (≈ the spec's `Family`) is the tenant root — `timezone` (default
`"Europe/London"`, drives calendar recurrence expansion) and `holidayMode` (household-wide
routine toggle, §15.4) live here, plus the `FamilyMember[]`/`CalendarEvent[]`/`Chore[]`/
`Routine[]`/`ShoppingList?` back-relations every other domain table hangs off.

**`FamilyMember`** is the household roster (§5.3) — distinct from `User`, the login account.
An adult has both: a `User`/`FamilyMembership` for auth, plus a `FamilyMember` card so they
appear in the roster alongside children (`linkedUserId`, unique, is the one-to-one tie; not a
join table, since an adult has exactly one card). A child has a `FamilyMember` row only, no
`User`/login. `role` (`ADULT`/`CHILD`) plus `linkedUserId` is what every "adults are read-only
except their own card, children are fully manageable" API check keys off (see API.md's
`family-members` routes). `(familyGroupId, name)` is unique — display names double as the
uniqueness key within a family, no separate slug.

**`LegacyUser`** is the pre-Better-Auth NextAuth user table, renamed out of the way so Better
Auth's Prisma adapter could own the `User` model name. Unused by app code; kept as a rollback
reference until `scripts/migrate-legacy-users.ts` has been run and verified in production,
then dropped in a later cleanup. **`AppConfig`** is an unrelated leftover from the original
kiosk-label scaffold (`app_label` row only) — nothing in the rewrite reads or writes it beyond
`GET /api/config`.

## Todos

**`Todo`** belongs to one `FamilyMember` (`userId` despite the name — predates the
`FamilyMember` rename). No due date in V1, so "today's todos" everywhere in the app (dashboard,
wall) really means "incomplete todos." `priority` is a plain boolean flag, no ordering beyond
it.

## Calendar

**`CalendarEvent`** always belongs to the `FamilyGroup`, never to one person —
**`EventParticipant`** is the join table to one or more `FamilyMember`s, unique on
`(eventId, familyMemberId)`. A recurring event stores an RFC5545 `rrule` fragment (built by
`lib/recurrence.ts` from a simple Daily/Weekly/Monthly preset) instead of persisted occurrence
rows; occurrences are expanded at read time with Luxon, using `FamilyGroup.timezone`.
Per-occurrence edit/exclusion (editing or deleting a single instance of a recurring event) is
explicitly future — editing/deleting always applies to the whole series today.

## Chores

**`Chore`** belongs to the `FamilyGroup` and is a definition, not a single item — it generates
daily **`ChoreOccurrence`** rows. **`ChoreSchedule`** is kept as its own table (rather than
columns on `Chore`) even though V1 enforces exactly one schedule per chore, so a future phase
can add rotation/multiple assignees without a migration; `daysOfWeek` uses JS `Date#getDay()`
convention (0 = Sunday .. 6 = Saturday). `ChoreOccurrence` is generated idempotently by
`generateChoreOccurrences` — unique on `(choreId, familyMemberId, date)` plus
`createMany({ skipDuplicates: true })` — and denormalizes `familyGroupId` from `Chore` so the
family+date index doesn't need a join. Completing/skipping an occurrence
(`setChoreOccurrenceStatus`) never writes back to the `ChoreSchedule` that produced it.

## Routines

**`Routine`** belongs directly to one `FamilyMember` (unlike `Chore`, where assignment lives
on the schedule) and is a named, ordered checklist (`RoutineItem[]`), not a single recurring
responsibility. **`RoutineSchedule`** mirrors `ChoreSchedule`'s shape (own table, same
`daysOfWeek` convention) plus `activeDuringHoliday` — the data-model hook for §15.4's "holiday
mode should allow disabling or an alternative schedule": V1 only implements "disable", so a
schedule defaulting `activeDuringHoliday = false` is skipped whenever
`FamilyGroup.holidayMode` is on. **`RoutineOccurrence`** is generated the same idempotent way
as `ChoreOccurrence`, unique on `(routineId, date)` — no separate `familyMemberId` in the key
because a `Routine` already implies a single assignee. **`RoutineItemCompletion`**'s existence
*is* the "checked" state (ticking upserts a row, unticking deletes it) rather than a boolean
column, so a `GET` of a day's occurrence never needs a separate reset step.

## Shopping

**`ShoppingList`** is `@unique` on `familyGroupId` — one shared list per family, created lazily
by `getOrCreateShoppingList` on first read/write rather than at family setup. Kept as its own
table (rather than items hanging directly off `FamilyGroup`) so a future "multiple lists"
option doesn't need a schema change. **`ShoppingItem`** is deliberately minimal: `name` and
`checked`/`checkedAt` only — no quantity, category, or store.

## Family isolation

There is no database-level tenant isolation (no RLS, no per-family schema) — every query that
returns or mutates domain data must filter by `familyGroupId`, either directly or via a
relation filter (e.g. `Todo`'s `where: { familyMember: { familyGroupId } }`). `lib/authz.ts#requireSession()`
is the only place a route derives `familyGroupId`, from the caller's session — it is never
accepted from the request body or query string. Every domain service function in `lib/`
(`calendar.ts`, `chores.ts`, `routines.ts`, `shopping.ts`) takes a `FamilyContext` (`{ user,
familyGroupId }`) as its first argument for this reason. `lib/authz.test.ts` has the unit
coverage for the permission layer this depends on; a family-isolation integration test (can
family A read/write family B's rows through the API) is still on the Testing Strategy backlog
— see `docs/ROADMAP.md`.

## Migrations

```bash
npx prisma migrate dev --name <change>   # create + apply locally (interactive terminal required)
npx prisma migrate deploy                # apply to Neon, using DIRECT_URL
npx prisma generate                      # regenerate the client after a schema edit
```

`prisma migrate dev` refuses to run non-interactively whenever it detects a rename or a
lossy drop — common once Better-Auth/`Invitation`-style migrations are involved. When that
happens, either run it in a real terminal, or hand-write the migration SQL (`prisma migrate
diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma
--script`, reviewed and placed under `prisma/migrations/<timestamp>_<name>/migration.sql`) and
apply it with `prisma migrate deploy`, which doesn't prompt. Vercel's build command (`npx
prisma generate && next build`) regenerates the client on every deploy, so a schema change
needs no separate manual step there — but a *migration* still has to be applied to Neon
explicitly, deploy doesn't do that.
